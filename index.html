一、央国企开发岗面试全景（先建立认知）

1.1 典型流程

网申 → 笔试（行测 + 专业知识）→ 专业面/技术面 → 综合面（半结构化）→ HR 面 → 体检 + 政审/背调 → 录用

有的单位把专业面和综合面合成一轮（多考官同场：一半问技术一半问综合素质）；部分单位有无领导小组讨论（群面）。

1.2 面试形式：结构化 / 半结构化

  • 结构化：所有候选人抽同样的题、同样时间、同样的评分表——像标准化考试；
  • 半结构化（最常见）：固定题 + 考官自由追问，追问多来自你的简历和前面的回答——所以简历每个词都是”自邀考点”。

1.3 和互联网面试的核心差异（策略调整依据）

维度 互联网大厂 央国企开发岗
技术占比 80%+，深挖原理和手撕代码 约 40-50%，广度 > 深度，基础概念说清即可
综合素质 几乎不问 权重很高：稳定性、价值观、团队、服从性、抗压
隐形考察 聪明、能卷 稳定、靠谱、留得住
加分认知 开源、新框架 数字化转型、信创（国产化替代）
礼仪着装 随意 正装、称呼”各位考官好”、离场致谢
反问环节 问技术栈 问培养机制、业务方向（不问薪资加班）

策略结论：技术按”每个概念 30 秒说清 + 一层追问”的标准（第三章）；项目按第四章深挖题准备；综合面按第五章逐题过；每题答案往”稳定、踏实、长期”的人设上靠。

3.1 第一行 · AI Application

Q1. RAG 是什么？ > 开卷考试：先从知识库里把相关材料翻出来，塞给大模型，要求它只照着材料回答。因为大模型不知道企业自己的数据，硬答会编。我在神农和中青旅都做过，优化过”翻错书”的各种毛病。 > 追问下限：检索用向量搜索+按条件过滤；生成时强约束”无依据就明说”。

Q2. Agent 是什么？ > 让 AI 不只动嘴还能动手干活的系统：模型决定调什么工具、填什么参数，系统真去执行再把结果喂回来。比如查实时门票库存这种事，模型自己不知道，就得调工具。 > 追问下限：我们用 LangGraph 把流程拆成节点编排，而不是让模型自由发挥。

Q3. 大模型的原理？为什么会有幻觉？ > 它在海量文本上训练”预测下一个词”，学会的是语言的统计规律——所以生成很流畅，但不知道的东西它没有”我不会”的机制，会一本正经地编。工程上用 RAG 给它供真实数据、用约束压住它别乱说。 > 追问下限：幻觉只能压制不能根除——检索给依据、提示词强约束、输出带出处可核查。

Q4. Prompt Engineering 是什么？ > 写好给模型的指令的技术。四要素：角色、任务、约束、输出格式（配示例）。最关键是约束——“只准依据给定材料回答，无依据则明说”是压幻觉的核心。 > 追问下限：改提示词必须过回归评测，防止修好一个坏三个。

Q5. Tool Calling 是什么？ > 模型输出一个结构化的”工具调用指令”（比如 查库存(景区=X, 日期=Y)），系统执行后把结果喂回模型。常见错误是参数填错——日期格式不对、ID 填错，解法是工具说明里写清参数格式。 > 追问下限：它返回的是可执行的指令不是聊天文本。

Q6. LangGraph 是什么？ > 一个把 AI 流程写成”流程图”的 Python 框架。理解成医院：分诊台（识别问题类型）→ 按病情分流 → 各科室干活（检索/调工具/生成答案）→ 病历本（状态对象）全程传递数据。可以理解为”用白盒方式构建 Agent”——整体流程由代码写死，个别环节允许模型自主。 > 追问下限：比黑盒 Agent 强在流程可控：强制先检索再生成、每步能打日志、出错能定位到节点。

Q7. Query Rewrite 是什么？ > 检索前先把口语问题改写成好检索的标准问——游客问”那学生呢”，先补全成”学生门票优惠政策”再去搜。不改写的话，指代不清、口语词根本搜不到东西。 > 追问下限：神农平台的第一个节点就是干这个的。

Q8. Metadata 是什么？ > “关于数据的数据”——数据本身之外那层结构化小标签。就像图书馆的编目卡片：找书不是通读全馆的书，而是先按分类号锁书架再翻。我们用在两处：①文档块打上景区 ID、生效时间等标签，检索先按标签过滤再语义搜索（“当前生效”这种精确条件靠语义搜索表达不了）；②指标词典——别名到标准指标到物理字段的三层映射表。一句话：大模型擅长”意思相近”、不擅长”精确相等”，Metadata 就是给它配的精确锚点。 > 追问下限：什么字段值得打标签——会被拿来过滤和统计的才打。

Q9. Metadata Filter 和 Rerank 分别解决什么？ > Filter 解决”范围”：先锁对本景区、当前生效的文档再搜——结构化条件，一个等号搞定。Rerank 解决”排序”：先粗召回 50 条，再用更精细的模型慢而准地挑出最好的 5 条——海选加复审。 > 追问下限：为什么不全部精挑——精挑每条几十毫秒，只能用在漏斗末端。

Q10. Text-to-SQL 难在哪？ > 就是让 AI 当翻译官：领导说人话，数据库只懂 SQL。三种典型翻车：把”回款额”翻译成”合同额”（听岔词）、漏翻”华东区、Q2”（漏条件，数字能查出来但口径是错的，最危险）、编造不存在的字段（瞎编，好在会当场报错）。 > 追问下限：解法是三段式——先查词典、列提纲、按提纲写，最后过”安检”。

Q11. AST 校验是什么？ > 生成的 SQL 过一遍”安检机”：把 SQL 解析成结构化的语法树（用 sqlglot），核对里面的表和字段是不是真的存在、必要条件带没带。不合格打回重写，再不行就降级用固定模板——保证返回的东西至少能跑。 > 追问下限：为什么需要——语法正确不等于表和字段真实存在。

Q12. Badcase 和回归评测是什么？ > Badcase 就是线上答错的案例。回归评测 = 错题本 + 模拟卷：错误按病因分类收进固定的题集，每次改系统（检索/提示词/工具配置）都先全量重考一遍，分数不退步才准上线——防止修好一个毛病带出三个新毛病。 > 追问下限：四类错误——没知识（库里没有）、过期政策（旧文档没清）、工具参数错、没依据硬编。

3.2 第二行 · Backend（Python、FastAPI 等；⚠java/SpringBoot 建议删）

Q13. Python 的 GIL？ > 全局解释器锁：Python 同一个进程里同一时刻只允许一个线程真正执行代码——所以多线程加速不了纯计算，计算密集要用多进程；但等待网络这类 I/O 场景多线程/异步没问题，我们的模型调用正是 I/O 密集。 > 追问下限：CPU 密集任务混进异步服务会卡死整个事件循环——丢进程池跑。

Q14. 装饰器和类型注解是什么？ > @app.post("/ask") 那种 @ 写法是装饰器：Python 里它在程序加载时就真的执行了，把你的函数登记进路由表——类似 Java Spring 的注解，但 Java 注解是被动标签要框架扫描，Python 装饰器是主动执行的代码。question: str 那个叫类型注解，本来只是备注，但 FastAPI 拿它实现了自动参数校验。 > 追问下限：装饰器一句话——“接收函数、返回函数的函数，不改函数本体给它附加功能”。

Q15. FastAPI 的开发模式是怎么回事？ > 我按它的格式写（装饰器登记 + 参数标注），给出业务逻辑代码；它负责整个流程——接请求、找到我的函数、校验参数、调用我的逻辑、把结果转成响应发回去。登记一次，之后全自动。这叫控制反转：普通脚本是代码驱动自己，框架是它驱动你的代码。 > 追问下限：函数内部的业务逻辑（检索、调模型）还是我写的，框架只负责”什么时候调用和进出转换”。

Q16. FastAPI、Starlette、Uvicorn 什么关系？ > 客服中心三层：Uvicorn 是接线员（服务器进程，守着端口接网络请求——没有它外界根本碰不到我的代码）；Starlette 是前台（把请求整理成标准单据、按地址分派给对应函数）；FastAPI 是坐席办公系统（让我写得舒服：路由写法、参数自动校验、自动文档）。日常我只跟 FastAPI 打交道，另两个装一次就不管了。 > 追问下限：ASGI 是异步服务器网关接口标准（对应同步时代的 WSGI）；为什么不用 Flask——Flask 同步，模型调用等几秒会把吞吐拖死。

Q17. RESTful API 是什么？ > 一套约定俗成的接口设计风格（不是技术）。三条规矩：地址表示东西（名词），HTTP 动词表示操作（GET 查 / POST 建 / PUT 改 / DELETE 删），无状态（服务器不记你是谁，每个请求自带全部信息，方便随时加机器扩容）。比如 GET /farms/42 就是”查 42 号田块”。 > 追问下限：状态码 200/404/400/429/500；“无状态怎么记住登录”→ 靠 token，凭证随每次请求自带。

⚠ java/SpringBoot：无出处支撑、与人设不搭，建议删除；若目标岗 JD 明确要 Java，改”了解 Java 基础”并补三天八股（HashMap 结构 / JVM 三大区域 / IOC 概念——IOC 就是 Q15 说的控制反转，Spring 靠它成名）。

3.3 第三行 · Retrieval & Data（SQL、Milvus、jieba、Redis、MQ）

Q18. SQL 手写（必须裸写）：

SELECT s.scenic_name, SUM(f.amount) AS total_income
FROM fact_finance f JOIN dim_scenic s ON f.scenic_id = s.id
WHERE f.year = 2026 AND f.quarter = 'Q2'
GROUP BY s.scenic_name ORDER BY total_income DESC;

追问下限：left join 保左表全量；where 过滤行、having 过滤聚合结果；索引像书的目录，避免一页页翻全表。

Q19. 事务 ACID？ > 四个保证：原子（一组操作要么全做成要么当没发生）、一致（数据从一个合理状态到另一个合理状态）、隔离（同时进行的操作互不捣乱）、持久（确认保存了就丢不了）。MySQL 默认隔离级别”可重复读”。 > 追问下限：并发三毛病——脏读、不可重复读、幻读，级别逐级解决。

Q20. 向量检索和关键词检索的区别？ > 向量认”意思”（问”优惠”能搜到写着”减免”的文档），关键词认”字面”（“戊唑醇”这种专业词一字不差才命中）。农业术语和冷门知识向量算不准，所以两个一起用，结果按排名融合（RRF——只用排名不用分数，因为两把刀的分数量纲不一样）。 > 追问下限：混合检索正是我们神农项目的做法。

Q21. Milvus 是什么？HNSW 是什么？ > Milvus 是向量数据库——专存”语义坐标”、回答”谁离我的问题最近”。HNSW 是它里面的索引结构（不是检索方式本身——检索是找最近，HNSW 是让找得快）：把向量组织成多层图，上层像高速公路快速逼近，底层像乡道精确到位，最终答案从最底层（全员层）的小范围精搜里出。牺牲一点准确率（95%+）换毫秒级速度。 > 追问下限：为什么近似可接受——top20 里漏一两条，整体问答无感；库百万级以内选 HNSW（吃内存换速度），亿级内存紧换 IVF（聚类分桶）。

Q22. jieba 干嘛的？为什么要灌自定义词典？ > 中文没空格，得先切成词（“小麦条锈病防治”→小麦/条锈病/防治）。jieba 用的是通用词典，不认识农业术语，会把”条锈病”切成”条/锈/病”——词被切碎等于不存在，关键词检索通道直接失效。所以我们整理农业词表（病名、药名、生育期术语），一行 load_userdict 灌进去，保证专业词整体切分。 > 追问下限：词表来源——领域资料 + 用户提问日志里挖高频词，越用越全。

Q23. Redis 是什么？ > 用内存存数据的键值数据库——内存比磁盘快十万倍，单机每秒 10 万+ 次读写。但它不只是快，还自带”自动化工具”：TTL（key 到期自动删——心跳 key 设 3 分钟，设备活着就一直续命，死了自动消失）、ZSet（按分数排序取——延迟队列：分数填到期时间，到点一把取出）、SETNX（原子占位——同一个位置只允许一个人占住，做幂等锁）。我们项目这四个用法全用上了。 > 追问下限：单线程为什么快（内存+epoll+免锁）；持久化 RDB 快照/AOF 日志，我们存的心跳数据可重建、对持久化不敏感。

Q24. 消息队列是什么？ > 两个程序之间的”传达室”：发消息的写张便条投进信箱就走（不用等谁来取），取消息的有空了来取，便条在信箱排队、不丢。解决三件事：解耦（发件人不用认识所有取件人，新订阅方零改动）、异步（投完就走，主流程不被拖慢）、削峰（一波消息涌进来先排队，下游按自己节奏取）。 > 追问下限：消息可能重复（处理完没来得及确认，传达室又发一份）→ 消费端必须幂等；延迟消息（指定 10 分钟后才能取）是”延迟确认”的实现载体。

Q25. 消息队列的消息是按顺序还是谁能取谁的？ > 两层：按”信箱”（主题 Topic）归类，取件人订阅信箱——不是每条消息写收件人，是人守着信箱。一个信箱两种玩法：多人抢着取（每条只给一个人——我们的巡检任务，100 个任务 10 个 worker 抢）或每家发一份拷贝（发布订阅——恢复事件，工单系统和分析组各拿一份）。信箱内先投先取，但多人同取或多分区时全局顺序不保证——需要严格顺序就按设备 ID 分格（同一设备的消息永远进同一格），我们工单闭环还用”执行前二次校验”兜住乱序。 > 追问下限：这就是为什么二次校验以数据库当前状态为准、不信消息顺序。

3.4 第四行 · ML

Q26. Transformer 的自注意力？ > 序列里每个时间点给其他时间点打”重要分”、按分数加权综合——“谁对我最重要”模型自己学。我们的场景：生育期序列里灌浆期权重自动升高，符合农学规律。 > 追问下限：注意力本身不识先后，要加位置编码——我们注入的是生育期阶段标记。

Q27. 为什么用 Transformer 不用 LSTM？ > LSTM 像逐字读文章，读到最后忘了开头（长序列前忘后），而且必须一个接一个算、没法并行；Transformer 全局直接建立联系 + 可并行训练。小麦生长季是典型的”长序列、关键期稀疏”结构，正适合。 > 追问下限：LSTM 靠门控（遗忘门/输入门/输出门）决定记什么忘什么，能说出即可。

Q28. GAT 和 GCN 区别？ > 都是图神经网络：节点=田块、边=地理邻近。GCN 对邻居”一视同仁”（权重按连接数固定）；GAT 让模型自己学”听哪个邻居的、听几分”——地里邻居影响本来就不均等，GAT 合适。 > 追问下限：GAT 流程——两节点特征打分、归一化成权重、加权聚合邻居信息，多头（几套独立打分）增强稳定。

Q29. 什么是过拟合？怎么防？ > 死记硬背训练数据、没学到规律——训练集上很好、新数据上拉胯。防法：早停（验证集不再变好就收手）、Dropout（训练时随机关掉一些神经元防死记）、控制模型规模、正确的数据划分（我们按年份留出——同年地块相关，随机划分会”泄题”）。 > 追问下限：为什么按年份不随机——就是防数据泄露。

Q30. 训练一个模型的完整流程？ > 数据对齐清洗 → 按年份划分 → 模型猜答案 → 损失函数打分”错多少” → 算出每个参数该往哪调（梯度）→ 小步调整 → 循环几百轮 → 验证集不再变好就停。 > 追问下限：学习率是步长——太大来回震荡不收敛，太小学得太慢。

Q31. 扰动归因和 IG 是一回事吗？（高频陷阱题） > 不是，是归因的三个家族：扰动是黑盒试错派（遮住某个输入看预测变多少，变化大=重要——像判断菜里哪种调料重要，每次少放一种尝味道）；IG 是白盒求导派（从基线到输入一路累加敏感度，解决”咸到头再加盐没感觉”的单点失灵问题）；SHAP 是博弈论分账派。我们选扰动：语义贴合”遮某段时期”、实现简单、特征少成本付得起。 > 追问下限：扰动法的坑——特征相关时会低估（成组扰动缓解）；IG 的坑——基线怎么选很敏感。

Q32. Git 的 merge 和 rebase 区别？ > merge 把两条分支拧成一股（保留分叉历史）；rebase 把你的提交搬到最新代码后面（历史一条直线更干净，但改写了历史）。工作流：开分支开发、合并前提 PR 让 mentor 审查。 > 追问下限：冲突怎么解——两人改了同一行，工具标出来人工选择保留哪边。

Q33. Linux 排查一个线上报错的过程？ > 场景化答：先 grep 'ERROR' app.log 定位报错时间点，再 tail -f 盯实时输出看复现，ps 看进程状态。比背 20 个命令有效。 > 追问下限：grep -C 3 带上下文三行；tail -n 200 看最近两百行。

Q34. Trace 排障是什么？ > 给每个请求发一个”编号”，它跨服务流转的每一步都记着这个号——排障时把一台设备的完整轨迹串成时间线。我在美团查误报就是拉一台设备的轨迹，把”判离线的时刻”和”最后心跳时刻”对齐，发现只差一个心跳周期——根因就出来了。 > 追问下限：和看日志的区别——日志是散的，Trace 串成线。

Q35. 接口联调是什么？ > 前后端（或多个系统）把接口对接调通：对字段名和格式、处理边界情况（参数没传、类型不对）。常用 Postman 手工调接口。经验：接口文档先行，联调能省一半时间。 > 追问下限：最常见的锅——两边对字段的理解不同步，所以要文档加评审。

4.1 美团 · 充电宝设备运营与异常治理平台（详版：01）

简历原文（北京三快在线科技有限公司 · 后端研发实习生 · 2026.06-2026.09）：

  • 总述：负责充电宝运营侧设备异常治理与巡检能力建设，围绕弱网场景下设备离线误报、异常工单无法及时闭环以及人工巡检成本较高等问题，参与存量业务规则优化及运营工具建设。
  • ① 设备异常误报治理：基于线上心跳Trace与设备事件日志排查弱网场景下状态频繁翻转问题，定位单次心跳超时即判离线导致的误报；参与将判定逻辑调整为连续失联窗口+恢复防抖，并通过历史事件回放验证阈值，最终同设备重复异常下降58%，离线误报率降低约21%。
  • ② 异常工单自动闭环：针对设备恢复后异常工单长期停留在待处理状态的问题，梳理设备状态事件→异常状态→工单状态流转关系，补充恢复事件监听、延迟确认与二次状态校验逻辑，使约46%的设备异常可自动完成闭环，减少人工确认操作。
  • ③ DeviceOps自动巡检：参与设备异常巡检任务开发，将长时间无心跳、状态不一致等人工排查规则沉淀为可执行巡检规则，并实现分片扫描、失败重试与结果记录；单轮巡检由约2小时缩短至20分钟以内，人工巡检工作量下降约40%。

Q1. 介绍一下这个项目？ > 平台负责全国充电宝机柜的监控、异常处理和巡检。机柜在商场餐厅走 4G 弱网，必须在线才能支持扫码借还。我参与三块工作：弱网误报治理（同设备重复异常降 58%）、异常工单自动闭环（46% 不用人工处理了）、人工巡检自动化（单轮 2 小时缩到 20 分钟以内）。

Q2. 心跳是什么？为什么会误报？ > 心跳是设备每 30 秒发一次的”我还活着”小包。地下室信号差，偶尔丢一两个包很正常，但旧逻辑是丢一个就判”离线”——把正常当异常，报警响个不停，运维白跑。

Q3. 防抖怎么做的？参数怎么定的？ > 两个方向都防抖：判离线要连续 3 个周期没消息（约 90 秒），不是丢一个就算；恢复后要稳定 5 分钟才算真回来（像退烧要观察一天不反复才算好）。参数不是拍的——拿历史日志回放，把窗口从 2 试到 10，画”误报率 vs 发现变慢”的权衡曲线选拐点。

Q4. 重复异常下降 58% 怎么统计的？ > 分子分母是治理前后”每台故障设备平均产生的异常条数”。核心改动是离线期间状态抖动不再重复记异常——一次故障只记一条，以前能记三五条。

Q5. 为什么不用机器学习做异常检测？ > 设备行为很简单（有心跳/没心跳），规则够用；规则可解释可回放，误报了能讲清原因，模型是黑盒没法向运营解释；误报直接产生人力成本，需要的是随时可调的机制不是要重训练的模型。要做”故障预测”那种复杂目标才值得上模型。

Q6. 工单闭环三步各防什么坑？ > 像请假销假：①监听恢复事件=装门铃，设备自愈有人知道（以前没人通知，僵尸工单堆积）；②延迟确认=观察 10 分钟再办，防止”假恢复”（弱网下冒个头又消失很常见）；③二次校验=办手续前再打电话确认——查一下设备当前真在线、工单没被同事领走，都确认才关单，防误关。

Q7. 为什么只有 46% 自动闭环？ > 剩下的 54% 是真异常：硬件坏了、断电没人管、设备被挪走，必须人上门。自动闭环的定位是消化”自己能好的”那部分，不追求 100%——硬提比例只会引入误关风险。

Q8. 分片怎么保证不重不漏？ > 按设备 ID 除以 100 取余数分 100 片——规则是固定公式，每台设备永远属于唯一一片，所有片合起来正好是全部设备，数学上保证不重不漏。10 个工人并行取任务，谁快谁多干。

Q9. 任务跑到一半挂了怎么办？ > 每处理完一台记一次进度（checkpoint），重试从断点继续不用从头来。就算整片重跑也没事——结果写入有去重键，同一台设备不会重复告警，幂等让重跑变成安全操作。

Q10. 这段实习最大的困难？ > 定阈值没有标准答案。“连续 N 个周期没心跳才判离线”听着是一行代码的事，但 N 取多少？两边都是代价：N 取大，误报少了，但真故障被发现得越来越晚；N 取小，发现快了，误报又回来了——没有两全的答案。我的做法是拿历史心跳日志做回放：把 N 从 2 到 10 逐个试，每个 N 都算出一组”误报率”和”平均发现延迟”，画成一条曲线。曲线前段很陡——N 从 2 到 3，误报率大幅下降；后面越走越平——再加大 N，误报率几乎不降了，延迟却一直在涨。那个”由陡变平”的位置就是拐点，N=3 就选在拐点上：用最小的发现延迟代价，换到了绝大部分的误报改善。这件事让我真正理解了什么叫数据驱动决策——不是找到完美答案，而是在两难里用数据找到性价比最高的那个点。

Q11. 犯过什么错？ > 巡检任务第一版我设计了”失败就整个重跑”，但没想过重跑的后果。联调时扫到第 60 台数据库卡了一下、任务失败，系统自动重跑——重跑是从头扫的，前面扫过的设备里命中过规则的又被记了一遍告警，同一台设备同一个问题，运营看到两条一模一样的告警，测试同学发现的。修复两刀：①给结果表加唯一键——同一台设备+同一条规则+同一个时间窗只允许存一条，重跑再插入同样的记录数据库直接拒绝，从此重跑多少遍都只记第一次（这就是幂等：做一次和做一百次效果一样）；②顺手把重跑改成从断的地方继续扫，连重复扫描都省了。教训：只要系统里有”重试”这个动作，就必须先问一句——重跑一遍，之前做过的事会不会再做一遍？

4.2 中青旅 · Text-to-SQL / RAG / Agent（详版：02）

简历原文（中青旅控股股份有限公司(央企) · 科技创新部 · 后端/AI应用研发实习生 · 2025.06-2025.09）：

  • 总述：围绕集团经营分析与智慧文旅问答场景，开展 Text-to-SQL、RAG 检索及 Agent 工具调用链路优化，重点解决指标理解偏差、知识召回错误与生成结果可信度问题。
  • ① 经营分析Copilot：基于真实经营问数Badcase排查 Text-to-SQL 错误，定位回款额、预算完成率、应收余额等问题中的指标误映射、组织/期间解析遗漏及字段幻觉；参与将生成链路拆分为指标解析、QueryPlan与SQL构建，并增加Metadata匹配及AST校验。基于218条典型问数回归验证，SQL可执行率由76.1%提升至89.4%（+13.3pp）。
  • ② 集团指标语义治理：针对景区、酒店、旅行服务等系统存在同名指标口径不同、同义指标字段不一致的问题，参与梳理指标定义、计算口径及来源字段，建立业务别名→标准指标→物理字段的Metadata映射；对存在多口径的问题增加指标消歧与澄清机制，累计沉淀126个核心指标、247组字段及别名映射。
  • ③ 智慧文旅RAG：基于线上咨询Badcase定位跨景区串召、过期政策误召回及长文档关键条件丢失问题，在向量检索基础上增加景区ID、生效时间等MetadataFilter，并采用父子Chunk+Rerank优化政策文档召回；在326条真实咨询问题集上，Top-5知识命中率由80.4%提升至90.2%（+9.8pp）。
  • ④ AIBadcase回归评测：围绕线上问答错误建立Badcase分类，重点覆盖无知识命中、过期政策、Tool参数错误及无依据生成等问题，并构建固定回归集验证Retrieval、Prompt与ToolCalling改动；累计分析137条典型Badcase、完成7轮策略迭代，核心问题端到端正确率由78.6%提升至87.3%（+8.7pp）。

Q1. 介绍这段实习？ > 集团两个 AI 场景：给管理层用的”用自然语言查经营数据”（Text-to-SQL），给游客用的”智能问答政策”（RAG）。我做了四块：问数链路优化（可执行率 76.1%→89.4%）、指标治理（126 个指标、247 组映射）、问答检索优化（Top-5 命中率 80.4%→90.2%）、以及贯穿全程的回归评测体系（端到端正确率 78.6%→87.3%）。

Q2. Text-to-SQL 三段式是什么？为什么拆？ > 以前是”一句问题直接生成 SQL”，错了不知道错在哪。拆成三段：指标解析（先查指标词典，把”回款额”锁定成唯一定义）、查询计划（列提纲，把”华东区、Q2”强制写成过滤条件）、按模板生成 SQL。三类错误各有专人拦：听岔词的词典拦、漏条件的提纲拦、编字段的最后安检拦。

Q3. 可执行率和正确率是一回事吗？（最常考） > 不是。可执行率 = SQL 能跑通不报错的比例；正确率 = 口径也对。最阴险的是漏了过滤条件的 SQL——照样能跑出数字，看着挺正常，实际查的是全公司全年。所以可执行率只是下界，我们另有人工抽检口径正确率。

Q4. 跨景区串召怎么定位、怎么解的？ > 每个回答都带”出处”标注，抽错误案例一看：召回的文档根本不是问的那个景区。根因是各景区政策文本太像（都是”XX 人群半价”就差景区名），语义搜索分不出来。解法是给文档打标签（景区 ID、生效时间），检索先按标签过滤再语义搜——一个等号解决的问题，不值得换更强的模型。

Q5. 父子 Chunk 为什么有效？ > 检索和生成对文本块的要求相反：检索要小块（语义集中搜得准），生成要大块（上下文完整不被断章取义——“仅限学生”和”半价”不能被切开）。父子结构解耦两者：小块拿来搜，命中后换成它所属的大块喂给模型。

Q6. Rerank 用的什么？ > bge-reranker。流程是海选加复审：向量搜索先快而粗地捞 50 条，精排模型慢而准地逐条细读挑出 5 条。代价是每条几十毫秒，但答案错误的代价（游客投诉、口径事故）远大于这点延迟。

Q7. 指标治理为什么是地基？ > 集团各系统黑话不统一：同一个东西 N 种叫法（入园人数/客流量/接待人次），同一个叫法 N 种含义（各家的”营收”口径不同）。翻译 AI 被这个害惨。我们编官方词典：各种叫法→标准名（带精确定义和口径）→仓库里的真实字段。126 个指标 247 组映射。AI 应用的上限取决于数据治理，不取决于模型——这是这段实习最大的认知。

Q8. 多口径指标怎么消歧？ > 解析置信度高就用默认口径，但答案里显式标注”按含税口径”；置信度低就反问用户，给选项不让开放填——宁可多问一句，不可猜错口径，错数字进了汇报材料是事故。

Q9. 回归集怎么用？ > 把错误案例和典型好题固化成一套不变的考卷。每次改检索、改提示词、改工具配置，先全量重考，各项正确率不许退步才上线。AI 系统改动的后果不可预测——教会它”没依据别乱答”，它可能变得过度保守；没有固定考卷，这种悄悄退步根本发现不了。7 轮迭代就是 7 次这个循环。

Q10. 这段最大的困难？ > 归因。同一个错误答案，检索、生成、工具五个环节都可能背锅。一开始只看结果就动手改，方向错过一次（以为要修提示词，实际那批题根本没检索到材料）。后来养成逐环节留痕：把检索结果、给模型的提示词、工具参数都打出来，先定位错在哪环再动手。

Q11. 为什么不微调一个模型？ > 三原因：标注数据只有百级，微调要千级以上；微调贵且慢，业务口径还在变；链路工程可解释可干预——出问题能定位到环节，微调是黑盒。而且基础模型一直在换代，链路方案换个模型能直接用。

4.4 MSTGN-Wheat · 科研项目（详版：04）

  • 项目描述：提出MSTGN-Wheat模型，融合遥感、气象与土壤多源数据，在田块尺度开展冬小麦产量估算；基于图神经网络建模地块间空间依赖关系，并结合生育期信息进行时空特征学习，有效提升预测精度与稳定性。

Q1. 介绍一下你的科研？ > 预测每块地能打多少小麦。数据三路：卫星看长势（植被指数）、气象（积温降水）、土壤（肥力）。模型两个核心：图注意力网络建模相邻地块的空间影响（小气候、土壤、病虫害都跨地块），Transformer 读生育期的生长日记（不同阶段对产量贡献不同，灌浆期最关键）。精度比基线相对提升 10-18%，产出了两篇 SCI。

Q2. 为什么要图结构？ > 空间影响是真实存在的：挨着的地气候土质相通、病虫害会传播——隔壁长势好你这块大概率也好。最有说服力的证据是消融实验：把图模块拆掉其他不变，精度明显下降——证明空间建模本身有效，不是堆料。

Q3. GAT 在模型里做什么？ > 节点是田块、边是地理邻近。注意力机制让每块地自己学”听哪个邻居的、听几分”——紧挨着长势典型的影响大，隔条河的可能没关系，权重是训练学出来的不是人定的。

Q4. 生育期信息怎么结合的？ > Transformer 的注意力本身不知道时间先后，需要额外注入”这是第几期”的标记——我们注入的是生育期阶段标签（返青、拔节、灌浆），等于告诉模型”这不仅是一个时间点，还是小麦生命的特定阶段”。模型学出来灌浆期权重高，和农学常识一致。

Q5. 多源数据怎么对齐？ > 最脏最重的活：卫星数据按田块边界聚合（一块地一个值）、不同来源的时间粒度统一重采样到每旬、云遮住的缺失期用前后插值补。数据对齐占了大半时间，但它决定上限。

Q6. 精度提升 10-18% 是相对谁？ > 四个基线：线性回归、随机森林、LSTM、还有拆掉图结构的自己。指标是均方根误差的相对下降——弱基线（线性回归）提升接近 18%，强基线（LSTM）约 10%，所以是区间不是单点。

Q7. 训练效率提升 30% 哪来的？ > 三件事合计：混合精度（用 16 位数字代替 32 位算，快且省显存）、多进程数据加载（不让显卡等饭吃）、图结构缓存（邻居关系不变，提前算好不重复建）。

Q8. 可解释性怎么做的？ > 扰动归因：把某个输入遮住（比如抹掉灌浆期的降水），看预测变了多少——变化大就是模型依赖它。判断一道菜哪种调料重要，每次少放一种尝味道变化。得到的重要性排序和农学规律一致（灌浆期气象权重高），说明模型学到的是真规律不是数据巧合——这也是农业模型能被信任的前提。

Q9. 泛化性怎么样？ > 跨区域会掉点——气候、品种、种植制度不同。诚实讲这是论文里也讨论的局限，跨区需要局部微调。讨论局限是科研素养，回避才是心虚。

1. 口语稿：项目介绍的两个版本

30 秒版（“介绍一下你的实习/项目”首选）

我在美团充电宝的设备运营平台做后端研发实习，这个平台负责全国充电宝机柜的设备监控、异常处理和巡检。我主要参与三块工作：一是弱网场景下的离线误报治理，把”单次心跳超时就判离线”改成”连续失联窗口 + 恢复防抖”，同设备重复异常下降了 58%，离线误报率降了约 21%；二是异常工单自动闭环，设备自愈后系统自动确认并关单，约 46% 的工单不再需要人工处理；三是把人工巡检规则做成自动巡检任务，分片并行扫描，单轮巡检从约 2 小时缩短到 20 分钟以内。

2 分钟版（面试官说”详细讲讲”时）

背景：充电宝机柜铺在商场、餐厅，走 4G 弱网，设备必须在线才能支持扫码借还。运营团队要监控设备异常、派工单、安排巡检。我实习时围绕三个问题做优化。

第一个问题是离线误报。原逻辑是丢一个心跳就判离线，但弱网下偶发丢包是常态，导致设备状态频繁在线离线来回翻转，一台设备一次故障被记成多条重复异常，运营被误报骚扰。我的做法是把判定改成”连续 N 个周期无心跳才判离线”，恢复时再加一段稳定期观察（我们叫恢复防抖，借鉴硬件按键消抖的思想），阈值不是拍脑袋定的，是用历史心跳日志做回放，画误报率和检测延迟的权衡曲线选的拐点。上线后同设备重复异常降了 58%。

第二个问题是僵尸工单。设备断电离线会生成异常工单，但很多时候来电后设备自己就好了，而旧系统不监听恢复事件，工单永远挂在待处理，运营每天人工销一堆单。我补充了”恢复事件监听 → 延迟确认 → 二次状态校验”的自动闭环链路：收到恢复消息不马上关单，先等 10 分钟确认稳定，执行关单前再实时查一遍设备状态和工单状态（防止误关运营正在处理的单），用 CAS 式更新防竞态。约 46% 的工单实现了自动闭环。

第三个是自动巡检。原来运营每周人工拉各种列表排查，一轮约 2 小时。我们把排查规则沉淀成代码，用设备 ID 取模分片、多任务并行扫描，带失败重试和断点续扫，单轮缩到 20 分钟以内，人工巡检工作量降了约 40%。

2. 系统全景

2.1 先用大白话理解

把充电宝机柜想成一群派驻在全国餐厅、地下室干活的员工：干活环境差（手机信号时好时坏），但必须随时联系得上，否则顾客借还不了充电宝。这个平台就是管家系统：盯着所有员工的状况，发现不对就开任务单，派人处理，定期体检。

管家系统当时有三个毛病，你的三块工作正好治这三个病：

  1. 报警器太灵敏：员工只是进了个电梯没信号，系统就喊”人失踪了！“——天天误报；
  2. 任务单没人销：很多员工睡一觉自己恢复了，但没人告诉系统，任务单永远挂着，堆成山；
  3. 体检靠老师傅人工翻本子：一查两小时，还容易漏。

2.2 展开讲：业务背景与链路

业务背景：充电宝机柜是 IoT 设备，用户扫码借充电宝的链路是”手机扫码 → 云端 → 通过长连接下发指令 → 机柜弹仓”。机柜离线 = 用户借还不了 = 直接损失收入。机柜联网环境差（地下室、商场深处），4G 弱网高丢包是常态。

4. 三大工作块详解

4.1 误报治理：连续失联窗口 + 恢复防抖

先用大白话理解

公司规定员工每 30 秒在群里报到一次。旧规矩：一次没报到就算”失踪”，立刻报警。地下室信号差，偶尔漏报一两次太正常了——于是警报天天误响，保安白跑，真出事反而没人当回事。

新规矩改了两处：① 连着几次（一分半钟左右）都没消息，才算真失踪；② 失踪的人重新冒头后，还得连续在线几分钟才算”真回来了”——就像孩子退烧了不能立刻宣布痊愈，要观察一天不反复才算好。防的就是”冒个头又消失”来回折腾。

展开讲

  • 根因：单次心跳超时即判离线 → 弱网丢包常态被当成异常 → 状态翻转 → 同设备重复异常刷屏。
  • 方案：两段式防抖——在线→离线需连续 N 周期无心跳；离线→在线需心跳持续稳定 M 分钟。Redis 维护失联计数器，超时 +1、收到心跳清 0，≥N 才翻转并生成异常；离线期间的状态抖动不再产生新异常记录（这是重复异常降 58% 的主要来源）。
  • 阈值确定：历史日志回放，N 从 2 遍历到 10，画”误报率 vs 平均检测延迟”权衡曲线选拐点。核心 trade-off：N 越大误报越少、但真故障被发现越晚（检测延迟 = N×心跳周期）。
  • 数字口径：重复异常 58% = 治理前后每台故障设备平均异常条数对比（回放可算）；误报率降约 21% = 被判离线中”实际没坏”的占比下降（以最终人工处理结果/后续心跳为 ground truth）；是”降低21%“不是”降到21%“，剩下的误报是断电、设备被挪走这类检测逻辑覆盖不了的。

4.2 工单自动闭环：监听 → 延迟确认 → 二次校验

先用大白话理解

员工生病了，公司开了张请假条（工单）。很多时候他睡一觉自己好了、正常回来上班了——但没人告诉 HR，请假条永远挂着，HR 每天手工销一堆”其实人早好了”的假条。

修这个流程就三步：①装个门铃——员工一返岗 HR 就收到通知（别再靠人肉发现）；②别急着销假——先观察一天，别是反复发烧那种假恢复；③销假前打个电话——确认人现在真在公司、假条也没被别的经理拿去处理中，都确认了才盖章。

展开讲

  • 根因：异常→工单有人写，设备自愈后没人监听恢复事件 → 工单永远”待处理”（僵尸单）。
  • 流程：心跳稳定满 M 分钟（复用防抖产物）→ 发 RECOVERY 事件到 MQ → 闭环消费者：①查有无”待处理”关联工单（无则结束，幂等）→ ②不立即关，丢延迟队列 10 分钟（延迟确认）→ ③到点二次校验：最后心跳是否新鲜 + 工单是否仍待处理 → CAS 关单（UPDATE ... WHERE id=? AND status='待处理'，影响行数 0 = 已被处理，放弃）。
  • 为什么三步缺一不可：没监听=自愈无人知晓；没延迟确认=假恢复导致开了关关了开；没二次校验=旧消息当现在事实，可能误关运营正在处理的单。
  • 为什么只有 46%：自动闭环定位是消化”自愈型异常”（断电后来电、网络波动后恢复）；硬件损坏、设备被挪走的必须人工现场处理。边界感是加分项。

4.3 自动巡检：规则代码化 + 分片扫描

先用大白话理解

以前有个老师傅，每天花 2 小时挨个翻记录本，检查”哪些设备不对劲”（多久没消息了、账本和实际对不对得上、电量正不正常）。

你做的事：①把老师傅的检查口诀写成程序，自动跑；②把检查任务分堆并行干——就像 2000 份试卷按学号尾号分成 10 堆，10 个助教同时改，一人一堆，谁快谁多干；③查到问题的拍照留证（记下当时的数据）；④某堆没查成的（比如系统卡了）老实记下来改天补查——绝不说谎假装全查完了。

展开讲

  • 根因：运营人工拉列表逐条排查（无心跳超 24h 但状态”在线”、接着电但电量长期低、槽位与借还流水不一致…），一轮约 2 小时。
  • 架构：定时调度 → 生成 run_id → 按片号拆 100 个任务进队列（任务只带片号，设备列表执行时查，shard_no 预计算建索引避免全表取模）→ 10 个 worker 并行消费（片数 > 工人数 = 天然负载均衡 + 失败重试粒度小）→ 片内分批加载（内存可控）逐台跑规则 → 命中写结果带快照（可审计）→ checkpoint 断点续扫 → 失败退避重试（5s/15s/45s）3 次仍败登记失败分片（巡检不撒谎：宁可承认 5% 没查到，不可谎报全查完）→ 全片完成计数齐 → 出报告。
  • 提速来源：并行（10 worker ≈ 墙钟时间 ÷10）+ 免人工拉表核对。2h→20min、人工量 −40%（40% 的原人工规则被系统覆盖并直接产出工单）。

5. 面试问答库

A. 项目总体类

A1. 介绍一下你的实习项目？ → 用第 1 章口语稿。先讲背景（为什么需要这个系统）再讲三块工作，每块带”问题→方案→数字”。

A2. 团队多少人？你具体负责什么，哪些是 mentor 帮你的？ 考察：诚实度 + 角色定位。实习生说”我一个人撑起整个系统”是重大减分项。 > 参考：团队负责整个运营平台，我的 mentor 是正式员工，负责整体方案设计和评审。我的工作是异常治理这一块的具体开发和验证：比如防抖逻辑的实现和回放验证脚本、闭环消费者的开发、巡检任务的分片改造。方案是我先出设计文档，mentor 评审提意见后我再动手，上线是走团队的灰度流程。

A3. 你怎么理解这个业务/为什么要做异常治理？ > 设备离线直接影响借还收入和用户体验；但比离线更隐蔽的是误报——每次误判都可能让运维白跑一趟，成本高且让运营对报警脱敏，真异常被淹没。所以治理的目标不是”消灭报警”，是把报警的信噪比提上去。

A4. 实习最大的收获是什么？ > 两点。一是工程上：学校做项目只关心”跑通”，这里学到每个改动上线前要回答三个问题——怎么验证（回放）、怎么灰度（按城市逐步放开）、出了问题怎么回滚。二是问题定位方法：先挑 badcase 拉 trace 还原时间线找根因，再改逻辑，而不是上来就猜。

B. 技术深挖类

B1. 心跳与误报

B1-1. 心跳周期多长？连续失联窗口取几？为什么？ > 心跳约 30 秒一次，窗口取连续 3 个周期（约 90 秒）。不是拍的：回放两周边历史心跳日志，把 N 从 2 到 10 遍历，N=2 时误报率还很高，N=3 相比 N=2 误报率降得最陡，再往后收益递减但检测延迟线性增加，所以选 3。真实故障场景下晚 90 秒发现是可接受的——工单处理本身是分钟到小时级的事。

B1-2. 为什么不直接用 TCP 断连判离线？ > TCP 断连只说明连接层断了，原因可能是 NAT 超时、基站切换、弱信号，设备本身是好的、马上会重连。离线是业务概念不是连接概念，所以用应用层的心跳超时来判。

B1-3. 为什么不用机器学习做离线检测？ > 四个理由：①设备行为模式简单（有心跳/没心跳），规则的判别力足够；②规则可解释、可回放验证，误报了能讲清为什么，ML 是黑盒，出问题没法向运营解释；③每次误报直接产生人力成本，需要的是可控、可调阈值的机制，规则调参立竿见影，ML 要重训；④开发和维护成本低。如果以后要做”故障预测”这种复杂目标，ML 才有价值。

B1-4. 恢复防抖具体怎么实现的？为什么是 5 分钟？ > 离线设备的心跳恢复后不立刻翻转状态，进”恢复观察期”，由延迟任务承载：到点检查这段时间内心跳是否连续稳定，中途再失联则计数清零、工单保持打开。M 的取值也是回放定的：统计”心跳恢复后 N 分钟内再次失联”的分布，取覆盖绝大多数真恢复的分位数。

B1-5. “58%”的分子分母是什么？怎么统计的？ > 分母是治理前每台故障设备在一次故障周期内平均产生的异常记录条数，分子是治理后的平均条数。因为离线期间的状态抖动不再重复记异常（一次故障只记一条），所以下降明显。用回放对比就能算，上线后的线上数据也验证了这个量级。

B1-6. 防抖会让真故障的发现变慢，这个代价怎么权衡的？ > 明确承认 trade-off：误报率换检测延迟。判断依据是业务容忍度——工单从生成到人工处理本身是小时级，多 90 秒检测延迟对业务几乎无感；但一次误报的代价是运维白跑一趟（几十分钟人力），所以方向上偏向压误报。

B2. 工单闭环

B2-1. 自动闭环的完整流程讲一遍？ > 用 4.2 的三步流程 + 凌晨断电来电的具体例子（见下）。面试官想听的就是三步各自防什么坑。

B2-2. 恢复事件重复消费/乱序怎么办？ > 消息队列是 at-least-once，重复和乱序都会发生。靠两层防护：消费端幂等——按设备+工单+动作做去重，关单用 CAS 式状态更新（WHERE status=‘待处理’），重复消息第二次执行时影响行数为 0 自然失效；乱序靠二次校验兜底——关单动作执行前以当前数据库状态为准，不以消息内容为准。

B2-3. 延迟确认用什么实现的？ > 延迟消息（MQ 的延迟级别）或 Redis ZSet 按到期时间排序、轮询到点任务。二者取舍：MQ 延迟消息可靠、级别固定（如 10 分钟档）；ZSet 灵活但轮询有空转和宕机恢复问题，需要持久化兜底。我们场景 10 分钟是固定档位，用延迟消息更简单可靠。

B2-4. 运营正在处理的工单被自动关掉怎么办？ > 这正是二次校验防的点：关单 SQL 带状态条件，工单一旦被运营领走变成”处理中”，CAS 更新影响行数为 0，自动关单自然放弃。即使极端时序下误关，关单记录了原因和快照，支持 reopen，且可追溯。

B2-5. 为什么自动闭环率只有 46%？剩下呢？ > 剩下的是真异常：硬件故障、断电无人恢复、设备被挪走，必须人工现场处理。自动闭环的定位是消化”自愈型异常”，不追求 100%——强行提高比例只会引入误关风险。

B3. 巡检与分片

B3-1. 分片怎么做的？怎么保证不重不漏？ > device_id % 100 切 100 片，分片规则是纯函数——同一设备永远属于同一片，所有片合起来恰好等于全量，数学上保证不重不漏。任务只带片号进队列，10 个 worker 并行消费，片数大于工人数实现负载均衡和小的重试粒度。

B3-2. WHERE device_id % 100 = 37 这种查询走不了索引，怎么办？ > 实际实现会预计算一列 shard_no 存在设备表里并建索引，或者按 ID 区间切分；片内再分批加载（每批几十台）控制内存。

B3-3. 任务跑到一半进程挂了怎么办？ > 片内每处理完一台记 checkpoint，重试从断点继续；即使整片重跑也安全，因为结果写入有去重键（设备+规则+时间窗），不会重复告警——幂等让”重跑”变成零成本的安全选项。

B3-4. 失败重试为什么要带退避？ > 失败大多是暂时性故障（DB 在备份、网络抖动），立刻重试等于往刚出问题的服务上再压一刀。退避（5s→15s→45s）给下游喘息时间；限定 3 次是止损——3 次都不行说明是真故障，登记失败分片等补扫，别耗着。

B3-5. 怎么知道一轮巡检扫完了？ > 完成片数/总片数计数器，全部回调齐才出报告。有失败分片则报告里显式标注覆盖率（如 97/100），绝不把”部分完成”当”全部完成”上报——巡检的价值在全覆盖，谎报比不查更危险。

B3-6. 命中的结果为什么要带快照？ > 数据是活的——半小时后设备可能被修复、状态被刷新。命中时把证据（最后心跳时间、DB 状态、电量、规则类型、时刻）一起落库，事后才能审计”这单为什么报上来”。命中≠确诊，快照是复核的依据。

B4. 基础设施延伸八股（从项目自然引出，必准备）

B4-1. Redis 在这个系统里怎么用的？ > 存设备实时状态热数据：device_id → 最后心跳时间戳/失联计数器，设 TTL 兜底（即使检测任务漏扫，key 过期也能触发）。追问 TTL 删除策略：惰性删除 + 定期删除；过期 key 大量堆积的问题答”我们按 device_id 分散过期，不会集中过期打崩”。

B4-2. 为什么用消息队列？ > 解耦 + 削峰 + 异步：设备状态服务和工单系统解耦，恢复事件、异常事件通过 MQ 传递；心跳高峰期事件量大，MQ 缓冲。追问丢失怎么办：生产端确认 + 持久化 + 消费端幂等（at-least-once + 幂等 = 效果上的 exactly-once）。

B4-3. CAS 更新是什么？为什么不用先查后改？ > 先查后改在”查”和”改”之间状态可能被别人改掉（竞态）。CAS 把条件和更新合并成一条原子 SQL：UPDATE ticket SET status='closed' WHERE id=? AND status='pending'，靠数据库行锁保证原子性，影响行数为 0 就说明状态已变。引申可讲乐观锁（版本号）与悲观锁（SELECT FOR UPDATE）的取舍。

B4-4. 幂等你们有哪几种实现？ > 三种都用到了：状态机 CAS（关单）、唯一键约束（巡检结果去重：设备+规则+时间窗）、Redis setnx（防并发重复触发）。核心思想：把”最多执行一次”转化为”执行多次但只有第一次生效”。

B5. 基础中间件小抄（MQ / Redis，从本项目长出来的概念）

MQ（消息队列）——两个系统中间的”快递柜”

  • 模型：生产者（发消息）→ 队列（排队，先入先出）→ 消费者（取消息）；双方不需要同时在场、不需要认识对方，只需要认识快递柜。
  • 三大价值（标准答案）：①解耦——发方代码里不写死收方，新订阅方零改动接入；②异步——发完就走，主链路不被慢操作拖住（打电话变发微信）；③削峰——流量洪峰进队列排队，下游按自己能力匀速消费（蓄水池）。
  • 项目位置：设备恢复事件（状态服务→工单系统）、巡检分片任务队列（100 个任务排队，10 个 worker 取）。
  • 投递语义：主流 MQ 是 at-least-once（至少一次，可能重复——消费完还没确认网络断了就会重投）。所以消费端必须幂等：“至少一次 + 幂等 ≈ 恰好一次”。
  • 延迟消息：发送时指定延迟，消息到点才可被消费——“延迟确认 10 分钟”的实现载体（RocketMQ 原生支持）。
  • 选型一句话：Kafka = 超高吞吐日志流；RocketMQ = 业务消息 + 原生延迟消息（本项目最合理）；RabbitMQ = 路由灵活、中小流量。
  • 追加追问：消息丢了怎么办（生产端确认 + 持久化 + 消费幂等各兜一层）；消息积压怎么办（扩消费者 / 批量消费 / 可重算的跳过）。

Redis——把热数据从仓库搬到桌面

  • 本质：内存键值数据库。内存 vs 磁盘差 10 万倍 → 单机 10 万+ QPS、亚毫秒延迟。类比：MySQL = 仓库（大、慢、持久），Redis = 桌面（小、快、断电就没）。
  • 五种结构 + 项目用法：String（device:42:hb → 心跳时间戳 + TTL）、Hash（设备实时快照：槽位/电量/信号）、List（简单队列）、Set（本轮已处理设备，天然去重）、ZSet（延迟队列备选：score = 到期时间戳，轮询取到期的）。
  • TTL 过期：惰性删除 + 定期删除；设备 key 按 device_id 分散过期，不会集中过期压垮 Redis。
  • 持久化：RDB（快照，恢复快、可能丢最近数据）/ AOF（命令日志，丢得少、恢复慢）；我们存的心跳类数据可重建，对持久化不敏感——能讲出这层比背定义高一个层次。
  • 单线程为什么快：内存操作 + epoll IO 多路复用 + 免加锁免切换；耗时命令会卡住所有人 → 生产禁 KEYS *，用 SCAN 渐进遍历。
  • 项目四位置：心跳时间戳 TTL 兜底 / 失联计数器（INCR/DEL）/ ZSet 延迟队列备选 / SETNX 幂等锁。
  • 追问预告：缓存穿透/击穿/雪崩、Redis 与 MySQL 一致性、分布式锁（SETNX + 过期时间 + 唯一标识）。

C. 难点与思考类（央国企最爱问的”困难与想法”）

C1. 这段实习遇到的最大困难是什么？ 考察：是否真做过。答”没遇到困难”或答纯生活困难都减分。 > 参考：最大的难点不是写代码，是定阈值时没有标准答案。把”单次超时判离线”改成”连续 N 周期”听起来一行代码的事，但 N 取多少？拍脑袋取 3，凭什么说服别人？当时的困难是：设备”实际在不在线”这件事没有直接的 ground truth——日志只告诉你心跳有没有到，不告诉你设备真实状态。最后的解法是拿两层近似标注：一是后续人工处理结果（最终被运维确认故障的），二是后续心跳是否长期恢复。用它们当基准做回放，才把 N 从”感觉”变成”数据”。这件事让我理解了工业界”数据驱动决策”不是口号，是真的在没有完美答案的场景里逼近答案。

C2. 你怎么定位到”单次超时判离线”这个根因的？ > 排查方法讲出来比结论重要：①先挑几台被运营反馈”误报”的设备，拉它们的 Trace 和事件日志，把”判定离线的时刻”和”最后心跳时刻”对齐，发现间隔只有一个心跳周期——丢一个包就判死；②再统计弱网区域设备的丢包间隔分布，确认”连丢两个包”是低概率、“丢一个包”是常态；③结论：判定阈值和丢包分布错配。修复方向自然就出来了。

C3. 方案设计上你做过什么取舍（trade-off）？ > 两个例子。①误报率 vs 检测延迟（B1-6）；②自动闭环的关单时效 vs 误关风险：延迟确认等 10 分钟会晚关单 10 分钟，但换来的是几乎零误关——工单晚 10 分钟关闭对业务无感，误关一张正在处理的单会浪费一次上门人力，所以选了保守。

C4. 如果重来一遍，你会改进什么？ > 两点：①防抖的阈值当时是全局统一值，其实不同网络环境（商圈/地下车库/写字楼）丢包特征差异很大，更优做法是按设备历史丢包率做个性化阈值或分档配置；②巡检规则和异常检测规则当时是两套配置，后期维护出现不同步，应该统一成一套规则中心的配置源。

C5. 上线流程是怎样的？怎么保证改动不出问题？ > 回放验证（离线先量化收益和风险）→ 测试环境跑真实流量回放 → 灰度（按城市/设备批次小流量放开，对比新旧逻辑的报警量、误报量指标）→ 全量。同时留监控看板盯核心指标，异常自动报警支持快速回滚。这套流程是我实习学到的最重要的东西——学校里”跑通就行”，工业界每个改动都要回答”怎么证明它没把别的东西搞坏”。

C6. 实习中犯过什么错？ 考察：自省 + 真实性。“没犯过错”不可信。 > 参考：巡检任务第一版我忘了做幂等，联调时任务失败重跑，同一台设备重复生成了两条告警，测试同学指出来才意识到。修复是给结果表加了”设备+规则+时间窗”的唯一键，顺手把重试逻辑从”整片重跑”改成了 checkpoint 断点续扫。教训：只要存在”重试”就要先想幂等，后来写任何消费逻辑都先设计去重键。

C7. 你怎么验证自己写的逻辑是对的？ > 三层：单元测试（判定逻辑是纯函数，喂构造的心跳序列断言状态转换）；回放（历史日志跑新旧逻辑对比，差异逐条人工抽查）；灰度期指标对齐（线上新旧逻辑并行跑一段，报警量/误报量在预期区间才全量）。

D. 央国企综合面类（半结构化面试常见）

D1. 自我介绍 > 1 分钟内：学校专业年级 → 技术方向（后端/AI 应用开发）→ 两段实习各一句（平台 + 最大成果数字）→ 科研/项目一句 → 与岗位的连接点。不背稿，练到自然。

D2. 为什么想来我们单位/这个岗位？ > 答题骨架：对单位业务的了解（提前查：主营业务、数字化方向）+ 自己的能力匹配点（设备运营/IoT 平台、AI 应用开发经验正好对应）+ 长期发展意愿（技术路线与单位规划契合）。避免空喊”平台大、稳定”。

D3. 实习中最有成就感的事？ > 用工单闭环那块：它不是炫技，是把一个”大家都知道烦但没人管”的问题系统化解决了，46% 的工单不用人工销——成就感来自真实减少了别人的无效劳动。（稳重、务实的叙事在央企面试更讨喜，比”性能优化了10倍”好。）

D4. 和 mentor/同事意见不一致怎么办？ > 骨架：先理解对方理由（对方的方案通常有我不知道的上下文/历史包袱）→ 用数据说话（把两个方案的回放结果摆出来）→ 仍不一致听 mentor 决策，执行中保留观察点。举例可编在阈值讨论上：我最初主张 N=4 更保守，mentor 提醒检测延迟对部分高价值商圈敏感，回放后 N=3 确实更均衡，我接受并补了分场景配置的后续优化项。

D5. 职业规划（3-5 年）？ > 稳健版：前 1-2 年把后端工程基本功打扎实（高并发、稳定性、规范流程），同时深耕 AI 应用工程化方向；3-5 年希望能独立负责一个业务域的技术方案，带小团队。央企版可加”愿意长期在单位发展、参与数字化转型项目”。

D6. 你怎么看加班/出差/值班？ > 如实但策略性：实习经历过版本上线值班，理解保障类系统有应急响应的需要，关键节点愿意顶上；同时表达会通过把事情做在前面（自动化、文档、预案）减少被动加班。不说”绝对接受无限加班”也不说”拒绝加班”。

D7. 你的优缺点？ > 优点配实习证据：拆解问题、用数据验证（回放、badcase 排查的故事可复用）。缺点选真实但不致命的 + 改进动作：如”实习初期过于追求方案完美、出方案慢，mentor 教我先用最小可行方案验证方向再迭代，后来好很多”。

D8. 反问环节问什么？ > 准备 2-3 个：团队目前的技术栈和主要业务方向？新人培养机制（导师制）？这个岗位未来一年最重要的目标是什么？——避免问薪资加班（终面 HR 环节再谈）。

E. 开放延伸类

E1. 如果设备量涨 10 倍，你的巡检系统要改什么？ > 分层答：①分片数和 worker 数可配置化，量涨就加片加工人，架构不变；②数据访问从单库查询演进到按分片路由（甚至读从库/物化视图），避免热点；③规则计算从”每轮全量”优化为”增量”——只扫自上轮以来有心跳变化的设备，静默设备走低频兜底扫描；④结果聚合从同步等齐改为流式汇总。

E2. 怎么发现”该优化误报”这件事的？ > 两个信号：运营侧反馈（每周例会抱怨误报多、销单烦）；数据侧（同设备异常条数分布的长尾——一台设备一个月几十条异常，明显不正常）。工业界的优化大多不是自己拍出来的，是从 badcase 和用户（内部运营也是用户）反馈里长出来的。

E3. 如果让你给这套系统加监控，你盯什么指标？ > 业务指标：误报率、同设备重复异常数、工单自动闭环率、巡检覆盖率与失败分片数。技术指标：心跳处理延迟、MQ 堆积、检测任务耗时、Redis 命中。原则：先盯业务结果指标（它们异常才说明系统真出问题），技术指标是定位手段。

1. 口语稿：项目介绍的两个版本

30 秒版

我在中青旅科技创新部做后端 / AI 应用研发实习，围绕集团两个场景做链路优化：经营分析问数 Copilot 和智慧文旅问答。问数是 Text-to-SQL 方向，我基于真实 Badcase 把生成链路从一步生成拆成指标解析、QueryPlan、SQL 构建三段，加上指标词典匹配和 AST 校验，在 218 条回归集上 SQL 可执行率从 76.1% 提到 89.4%；同时参与集团指标语义治理，建了 126 个核心指标、247 组别名到物理字段的映射。问答是 RAG 方向，用 Metadata Filter 解决跨景区串召和过期政策误召回，用父子 Chunk 加 Rerank 优化召回，326 条真实问题集上 Top-5 命中率从 80.4% 提到 90.2%。全程建了 Badcase 回归评测体系，7 轮迭代把核心问题端到端正确率从 78.6% 提到 87.3%。

2 分钟版

中青旅是央企文旅集团，旗下有景区、酒店、旅行社业务线。我实习的科技创新部做两个 AI 应用。我的工作重点是解决指标理解偏差、知识召回错误、生成结果可信度三类问题。

第一个是经营分析问数 Copilot，让分析师用自然语言查数。排查真实问数 Badcase 后发现三类错误：指标误映射（问回款额查成了合同额）、组织和期间条件遗漏（漏了 WHERE 过滤，数字能跑出来但口径是错的）、字段幻觉（编造不存在的字段）。我把一步生成的链路拆成三段：指标解析先查指标词典锁定标准指标，QueryPlan 强制把组织和期间写成过滤条件，SQL 构建按模板拼装，最后过 AST 校验——用 sqlglot 把 SQL 解析成语法树，核对表和字段真实存在。218 条回归集上可执行率从 76.1% 提到 89.4%。

第二个是配套的指标语义治理：集团各业务系统同名指标口径不同、同义指标字段不一，我们梳理出业务别名→标准指标→物理字段的三层映射，126 个核心指标、247 组映射，多口径指标加了消歧和反问机制。这是指标解析的地基。

第三个是智慧文旅 RAG。线上 Badcase 集中在三类：跨景区串召（各景区政策文本太像，向量分不清）、过期政策误召回（旧版政策还在库里）、长文档条件丢失（限定句和条款被切分切开了）。解法是 Metadata Filter——按景区 ID、生效时间先过滤再语义检索；父子 Chunk——小块做检索、命中后取大块保上下文；再加 Rerank 精排。326 条问题集上 Top-5 命中率从 80.4% 提到 90.2%。

最后是贯穿全程的 Badcase 回归评测：错误按无知识命中、过期政策、Tool 参数错误、无依据生成分类，固化成固定回归集，任何检索、Prompt、工具配置的改动都要全量重跑、指标不许退化才能上线。7 轮迭代，端到端正确率从 78.6% 提到 87.3%。

2. 系统背景与两条链路

2.1 先用大白话理解

集团里两件烦事：

第一件：领导想看数字，得配个翻译。 领导问”华东区上半年回款多少？“——数据都在电脑仓库里，但仓库只听得懂一种很专业的话（SQL），领导说的是人话。以前得靠懂数据库的人当中间翻译。我们要做的，就是让 AI 来当这个翻译：领导说人话，AI 翻译成仓库的话，去查，报数。

第二件：游客问政策，得有人翻书。 游客问”退役军人门票有优惠吗？“——答案在几百份政策文件里。AI 大模型自己其实并不知道答案，硬答就会编。所以要让它开卷考试：先把相关政策那几页翻出来，摆在它面前，命令它”照着这段回答”。

你的实习就是给这两个系统修毛病：翻译官经常翻错（第一块工作），各公司的”黑话”不统一害的（第二块），翻书经常翻错页（第三块），以及给整个系统建一套”改完必须复考”的规矩（第四块）。

2.2 展开讲：业务背景与链路

业务背景：央企文旅集团（景区如乌镇/古北水镇、酒店、旅行社），科技创新部。两个场景：

  • 场景 A · 经营分析问数 Copilot：给高管/财务/分析师用，自然语言问数（“华东区 Q2 回款额”），系统生成 SQL 查数仓返回结果。技术方向：Text-to-SQL（自然语言转 SQL）。
  • 场景 B · 智慧文旅问答：给游客/客服用，问政策（“退役军人门票优惠吗”），系统检索政策文档后由 LLM 作答。技术方向：RAG（检索增强生成）。

3. 地基概念卡片（8 张，第二遍读时逐张过关）

① LLM 与 Prompt（大语言模型 与 提示词）：LLM 是”接话机器”，给它一段文字（Prompt）它续写。它没有你们公司的数据、知识冻结在训练截止日——这个知识边界是所有工程的原因。

② 幻觉（Hallucination）：LLM 不知道也照答、编得有鼻子有眼。无法从模型层面根除，只能工程压制——简历上所有工作的本质都是在压幻觉。

③ Embedding 与向量检索（向量化 与 语义搜索）：把文字变成”语义坐标”（一串浮点数），意思近的坐标近。向量检索 = 拿问题坐标找最近的文档片段——认意思不认字面（“门票优惠”能搜到”票价减免”）。

④ RAG（检索增强生成）：开卷考试。先检索相关段落塞进 Prompt，要求模型”只准根据材料回答”——从”凭记忆瞎编”变”照着材料念”。

⑤ Tool Calling / Agent（工具调用 / 智能体）：让模型输出结构化的工具调用指令（查库存(景区=X, 日期=Y)），系统执行后把结果喂回。“Tool 参数错误”= 模型填错参数（日期格式非法、景区 ID 错）。

⑥ Copilot（副驾驶）：嵌在工作流里的 AI 助手——人做决策，AI 提效。Copilot ≠ Autopilot（自动驾驶）：人在回路里，最终确认由人负责（企业场景的可追责性）。两个设计是它的体现：多口径时反问澄清、答案标注所用口径。

⑦ Metadata（关于数据的数据）：内容之外的结构化小标签，类比图书馆编目卡片——找书先按分类号锁书架再翻内容。项目里两处：文档块的标签（景区 ID/生效时间 → 检索先过滤）、指标的词典（别名→标准指标→物理字段）。语义靠向量，精确靠 Metadata——LLM 是模糊的概率系统，Metadata 是钉进来的结构化锚点。

⑧ Badcase（坏例子）：线上答错的真实案例。Badcase 分析是所有优化的起点：先收集归类，才知道该修哪。

4. 四大工作块详解

4.1 经营分析 Copilot（Text-to-SQL）

先用大白话理解

AI 翻译官把领导的人话翻译成数据库的话，犯的错就是翻译的三种事故：

  1. 听岔了词：领导问”回款额”（实际收回来的钱），翻译官翻成了”合同额”（签了多少钱）——俩词长得像，意思完全不同；
  2. 漏听了限定词：领导问”华东区、上半年的回款额”，翻译官把”华东区”“上半年”漏了——翻出来的话语法完全正确，也能查出一个数字，但那个数字是全公司全年的。最阴险：数字看着挺正常，错进汇报材料都没人发现；
  3. 瞎编了一个词：翻译官写了个数据库里根本不存在的词——好在这种错当场穿帮（数据库直接报错），反而危害最小。

治法是把”听题直接翻”改成专业流程：动笔前先查术语词典（“回款额”在词典里查到唯一对应）、先列提纲再写（把”华东区”“上半年”强制写成限定条件）、写完过一遍安检机（核对每个词库里真有）。

展开讲

是什么：翻译官——用户说人话，数仓只懂 SQL。旧做法把问题直接丢 LLM 一步生成，错误无规律、不可归因。

三段流水线（把一步翻译变成专业翻译流程）：

  1. 指标解析（查词典）：问题 + 指标 Metadata 给模型，只输出结构化结果 {指标, 组织, 期间}——误映射在词典被拦；
  2. QueryPlan（查询计划，列提纲）：确定查哪些表、过滤条件、聚合方式、分组维度——组织和期间强制写成过滤条件，漏条件在这里堵住；
  3. SQL 构建（按提纲动笔）：按 Plan + 表元数据模板化拼装——字段都来自真实元数据，幻觉空间大幅压缩。

AST 校验（安检机）：AST（抽象语法树）= 把 SQL 文本解析成的树状结构（“用了哪些表、哪些字段、什么条件”的结构化表示，用 sqlglot 实现）。核对：表名存在？字段属于这张表？时间/组织过滤带了吗？不合格打回重生成（有限次数），仍失败降级模板 SQL。

数字口径：218 条回归集（真实 Badcase + 高频问题沉淀）；可执行率 76.1%→89.4%。必须会说：可执行率是下界——漏 WHERE 的 SQL 照样能执行！字段幻觉的修复直接体现在可执行率，①②类靠词典和 Plan 堵、体现在人工抽检的口径正确率上。为什么报可执行率：它能自动化统计。

4.2 集团指标语义治理

先用大白话理解

集团旗下景区、酒店、旅行社各公司各系统建了多年，“黑话”严重不统一，两种病：

  • 同一个东西 N 种叫法：“土豆 / 马铃薯 / 洋芋”其实是一个东西——集团里”入园人数 / 客流量 / 接待人次”就是一个指标的三种叫法；
  • 同一个叫法 N 种含义：“苹果”既可以是水果也可以是公司——“营收”在景区公司=门票+园内消费，在酒店公司=房费+餐饮，字面一模一样，含义完全两回事。

AI 翻译官被这两种病害惨（听岔词的一大根源）。治法：编一本全集团官方词典，三层结构：各种叫法（方言）→ 标准名+精确定义（普通话）→ 仓库里的货架号（身份证号）。遇到”营收”这种一词多义的，词典标出来，系统反问一句：“您要含税口径还是不含税口径？”——宁可多问，不可猜错。

展开讲

三层映射：

业务别名(用户叫法)      标准指标(唯一ID+定义+口径)      物理字段(数仓落点)
回款额、已回款金额  →   指标#017: 已实际收到的合同款项 → dws_fin.received_amount
入园人数、客流量    →   指标#042                      → dws_scenic.visitor_cnt

口径 = “这个数怎么算出来的”的官方说法（营收含不含税、退款扣不扣）。126 个指标、247 组映射：247 > 126，一个指标平均约两个别名/字段——这个数量关系要能解释。

消歧与澄清：多口径指标（如”营收”）——解析置信度高 → 自动选默认口径 + 答案里标注所用口径；置信度低 → 反问用户（“含税还是不含税？”）。

定位：第一块的地基。面试升华点：“AI 应用的上限往往取决于数据治理，不取决于模型。”

4.3 智慧文旅 RAG

先用大白话理解

AI 开卷考试翻书（政策文档库），翻错的方式就三种，各有各的药：

  1. 拿错了书：游客问古北水镇，它翻到了乌镇的政策文件——因为各景区的政策写得太像了（都是”XX 人群半价”，就差景区名），“按内容相似度找”这招分不出你我。药：翻书之前先把书架锁对——只在本景区、今年生效的文件里找；
  2. 翻到了旧书：书架上 2024 旧版和 2025 新版票价并排放着，旧版写得反而更规整、更容易被”内容相似度”选中。药：还是锁书架——书架上只留当前生效的版本；
  3. 断章取义：一份政策开头写”仅限全日制学生享受以下优惠”，后面某条写”门票半价”。文件被切碎存档时，“仅限学生”和”半价”进了两个袋子——翻书只翻到”半价”那个袋子，谁来问都答半价。药：袋子做小卡片用（小卡片好定位），翻到之后展开成整页再读（整页上下文完整）。

最后再加一道工序：先快速圈出 50 份候选（快但粗），再一份份细看挑出最好的 5 份（慢但准）——海选 + 复审。

展开讲

Badcase 类比 根因 解法
跨景区串召 拿错了书 各景区政策句式几乎一样，只差景区名，向量分不清 Metadata Filter
过期政策误召回 旧书没下架 新旧版本都在库里，旧版文本更”规整”相似度反而高 Metadata Filter（生效时间）
长文档条件丢失 断章取义 “仅限全日制在校生”和”门票半价”被切进两个块 父子 Chunk
  • Metadata Filter（元数据过滤）= 先锁书架再搜内容：入库时给块打结构化标签（景区 ID、生效/失效时间、政策类型），检索先过滤再语义搜索（pre-filter，先过滤避免召回后再滤导致数量不足）。为什么必须靠标签：①景区 ID 是精确字段，一个等号解决，语义分不清；②”当前生效”这种日期逻辑向量检索根本表达不了。
  • 父子 Chunk（父子切块）= 索引用小卡片，阅读展开整页：检索要小块（语义集中、向量不被稀释），生成要大块（上下文完整）——解耦两个需求。子块（约 200 字）入向量库被检索；命中后替换成父块（约 1000-2000 字或完整章节）送 Prompt。限定句和条款大概率同属一个父块。
  • Rerank（重排序/精排）= 海选 + 复审：向量检索快但粗（只看语义坐标粗略距离）→ 海选 top50；交叉编码器（如 bge-reranker，把问题和文档拼一起精细打分）慢但准 → 复审取 top5。漏斗：全库几万块 → 海选 50 → 精排 5 进 Prompt。Rerank 每条几十毫秒，只能放漏斗末端——这就是不能全库精排的原因。

数字口径：326 条真实咨询问题集（人工标注每个问题的标准出处）；Top-5 命中率 = 前 5 块中至少含 1 个正确出处的比例，80.4%→90.2%。剩余 ~9.8% 是检索解决不了的：知识库本身缺内容、问题歧义、需跨文档多跳推理——边界感要讲得出。

4.4 Badcase 回归评测（错题本 + 模拟卷）

先用大白话理解

AI 系统像学生：你改了它的”学习方法”（调整配置），可能治好了老毛病，也可能悄悄弄出新毛病——不考试你根本不知道。

做法全是学校那套：把线上答错的题收进错题本，按病因分四堆——课本里没这知识（库里没这政策）/ 翻到了旧版教材（过期政策）/ 计算器按错了键（工具参数填错）/ 不会做还瞎编（没依据硬答）。每次改系统之前，把整本错题本加上本来就会的题，重新考一遍：分数没退步才准改，退步了就打回。改了 7 轮，成绩从 78.6 分涨到 87.3 分。

为什么这么死板？因为 AI 系统改动的后果不可预测：你教它”没依据别乱答”，它可能变得过度保守，好多本来会的也不敢答了——错题本就是防这种”悄悄退步”的唯一手段。

三个可调旋钮：Retrieval（检索，换翻书方式：加 Filter、调切块、调召回量）、Prompt（提示词，改答题规矩：只准依据材料、必须附出处）、ToolCalling（工具调用，修工具使用：说明更清楚、参数给示例）。

“回归”的含义：来自软件测试 regression test（回归测试）——改完代码重测旧功能，确认没退步。AI 系统的顽疾是改动不可预测，固定回归集是防”悄悄退步”的唯一护栏。

5. 面试问答库

A. 项目总体类

A1. 介绍一下这段实习？ → 第 1 章口语稿。结构：背景（两个场景）→ 三类问题 → 四块工作各带”问题→方案→数字”。

A2. 你具体负责什么？ > 参考口径：团队负责两个系统的整体架构，我的 mentor 把关方案。我负责的是链路优化里的具体工作：Badcase 的收集分析和归类、三段式链路中指标解析和 AST 校验的开发、治理表条目的梳理和映射关系整理、RAG 侧 Metadata 入库改造和父子切分方案、回归集的构建和评测脚本。方案我出设计、mentor 评审后动手，改动能过回归才上线。

A3. 两段实习（中青旅 vs 美团）有什么区别和联系？ > 考察叙事能力，标准答案：“技术底座相同——都是事件/数据链路上的工程问题，方法论一致：Badcase 驱动、先定位根因再改、改动要可验证。区别在问题域：中青旅是 AI 应用的可信度问题（幻觉、口径、召回），美团是分布式系统的稳定性问题（误报、状态一致、幂等）。中青旅教我 AI 工程化，美团教我后端工程素养，我想要的方向正是两者交叉——AI 应用的后端化。”

A4. 这段实习最大的收获？ > “一句话：AI 应用的上限取决于数据治理而不是模型。指标误映射的解法不是更强的模型，是一张治理表；串召的解法不是更好的 Embedding，是结构化过滤。第二个收获是质量意识：没有回归评测的 AI 系统每次改动都是赌博。”

B. 技术深挖类

B1. Text-to-SQL

B1-1. 为什么把一步生成拆成三段？ > 一步生成是黑盒：错误无规律、不可归因、不可拦截。拆段后每段职责单一，三类错误各有人拦——误映射在词典、漏条件在 Plan 强制、幻觉在模板+AST。而且每段可独立测试和优化，出了错能精确定位到段。

B1-2. AST 校验具体校验什么？失败了怎么办？ > 用 sqlglot 把 SQL 解析成语法树，核对四件事：表名在 schema 里存在、每个字段真的属于所查的表、必要过滤（时间/组织）存在、无异常嵌套。失败带错误信息重新生成（限 2-3 次），仍失败降级用模板 SQL，保证一定返回可执行结果。

B1-3. 可执行率和正确率是一回事吗？ > 不是，这是我最注意区分的口径。可执行 = 语法和对象合法、能跑通；正确 = 口径也对。漏了组织过滤的 SQL 照样能执行、返回一个看起来正常的数字——最危险。可执行率能自动化统计所以作为主指标，同时人工抽检语义正确率，两者一起看。

B1-4. 表结构（schema）怎么给模型？全给吗？ > 不全给，表多字段多会超上下文且干扰生成。按问题先检索相关表（表名/描述/字段也做成 Metadata 做检索），只把相关表的 schema 放进 Prompt。

B1-5. 为什么不微调一个模型，而用 Prompt + 链路工程？ > 三个原因：标注数据量不够（Badcase 才百级，微调要千级以上）；微调迭代慢、成本高，业务口径还在变；链路工程可解释可干预，出问题能定位到环节，微调是黑盒。且基础模型在迭代，链路方案可平移换模型，微调绑定。

B1-6. 218 条回归集会不会”改到只对回归集生效”？ > 有这个风险（过拟合回归集）。措施：回归集留一部分做 held-out（改策略时不见）；新 Badcase 持续补充进来；上线后看线上指标和回归指标是否同步变化，不同步就说明过拟合了。

B2. 指标治理

B2-1. 126 个指标怎么选出来的？ > 三个来源取交集：问数日志里的高频词、财务核心指标（回款/预算/应收这些必问的）、三大业务线（景区/酒店/旅行服务）各自的主线指标。先覆盖最高频的 126 个，长尾的按需扩。

B2-2. 别名从哪来的？ > 问数日志挖掘（用户实际怎么叫）+ 业务方访谈确认 + 同义词扩展，全部人工审核后入表。别名是会长出来的，治理表是活文档。

B2-3. 消歧具体怎么实现？ > 指标解析段让模型输出”命中指标 + 置信度”。多口径指标：置信度高 → 用默认口径，但答案里显式标注”按含税口径”；置信度低 → 生成澄清问题反问用户，给选项不给开放题。原则：宁可多问一句，不可猜错口径。

B3. RAG

B3-1. Embedding 用的什么模型？为什么？ > bge 系列（bge-large-zh-v1.5 / BGE-M3），1024 维。理由：中文效果好于通用模型、开源可私有化部署——央企场景数据不出内网，这是硬约束；生态成熟，配套 reranker 同系列。

B3-2. 父子块具体怎么配的？ > 子块约 200 字、按语义段落切（标题/条款边界优先）；父块约 1000-2000 字或完整章节。子块入向量库，块记录 parent_id；命中子块后按 parent_id 取父块（同父的多个子块去重合并）进 Prompt。

B3-3. Rerank 用的什么？延迟代价？ > bge-reranker 交叉编码器。海选 top50 → 精排取 top5。每条打分几十毫秒、50 条总增量两三秒内可控（可批量并行）；换来精度提升明显，值得。

B3-4. 为什么不用 BM25 关键词检索？ > 关键词认字面：用户问”优惠”，文档写”减免/打折”就召回不到。语义检索解决这个。但我们不是二选一——保留关键词通道做混合检索（RRF 融合两者排名），政策编号、景区名这类精确词关键词更稳，语义和精确各取所长。

B3-5. Metadata Filter 是先过滤还是后过滤？ > 先过滤（pre-filter）：先用结构化条件把候选集缩小到本景区、当前生效，再在缩小后的集合里做向量检索。反过来（先召回再滤）会出现召回 50 条滤完只剩 3 条、数量不足的问题。

B3-6. 剩下 9.8% 没命中的是什么？怎么办？ > 三类：知识库缺内容（检索再好也无米下锅——补知识库）、问题本身歧义（需澄清）、需要跨文档多跳推理（要 Agent 拆解）。我的边界认知：检索优化能解决”找得准”，解决不了”库里没有”。

B3-7. Top-5 命中率怎么定义的？ > 人工给 326 个问题标注”标准出处”（正确答案来自哪个文档哪些段落），检索前 5 块里至少含一个正确出处即算命中。标注有规范，双人标注抽检一致性。

B4. 回归评测

B4-1. 正确率谁来判？ > 人工标注为主。量大时用 LLM 辅助初判（按评分标准给通过/不通过），但定期人工抽检校准 LLM 判断的一致率——LLM 当裁判本身也会错，所以只能当初筛。

B4-2. 回归集多大才够？ > 没有绝对数，标准是：覆盖的每类高频错误有足够样本（每类至少几十条）、加上等比例的”本来就能答对”的题（否则只防复发不防误伤）。回归集是滚雪球的，新 Badcase 持续补进来。

B4-3. 一次迭代的完整流程？ > 线上发现/用户反馈 Badcase → 归类、补进回归集 → 本地改动（检索/Prompt/工具）→ 全量重跑回归 → 出对比报告（每类指标变化）→ 评审通过才上线 → 线上监控正确率。7 轮迭代就是 7 次这个循环。

B4-4. 线上怎么发现 Badcase？ > 三个渠道：用户反馈（点踩）、客服上报（答错被游客投诉的）、定期抽检。回流有责任人和周期，不是等出大事才发现。

C. 难点与思考类

C1. 这段实习最大的困难？ > “Badcase 的归因。同一个错误答案，可能是检索没找到、找到了没排进前五、排进了但 Prompt 没放好、模型没遵守指令、工具参数错——五环都可能背锅。一开始只看最终答案对错去改，方向判断错过一次：以为是不瞎编的 Prompt 问题，实际是那批题检索根本没召回，改 Prompt 无效。后来养成的习惯是逐环节留痕：把每次的检索结果、组装后的 Prompt、工具调用参数都打出来，先定位错在哪一环再动手。这个调试习惯是这段实习最硬的收获。”

C2. 你怎么定位”跨景区串召”这个问题的？ > 抽 Badcase 看系统自带的出处标注（每个回答附带引用的文档块），统计发现召回块的景区 ID 和问题景区不符的比例很高；再看根因：各景区优惠政策文本句式高度相似只差景区名，纯向量检索分不出来。结论是这不是”语义不够像”的问题，是”检索范围没锁对”——所以解法是结构化过滤而不是换 Embedding。

C3. 做过什么取舍？ > 两个。①Rerank 的精度 vs 延迟：加精排整体响应增加，但答案错误在客服场景的代价（投诉、口径事故）远高于几百毫秒，值得；②反问澄清 vs 直接答：反问多一轮交互、体验有损，但口径错误进了汇报材料是事故级代价——企业场景一律选准确性优先。

C4. 犯过的错？ > 同 C1 的例子：没做逐环节归因就改 Prompt，一轮迭代白做。教训：AI 链路里”最终答案错”≠“生成环节错”，必须先看中间结果。后来我把”打印中间态”固化成了调试规范。

C5. 如果重来会改进什么？ > ①回归集从第一天就该建，而不是先改了几轮才补——前几轮改动其实没有护栏；②Badcase 分类体系一开始定得太粗，中途重构过一次，应该先参考成熟分类（检索类/生成类/工具类）再细化；③治理表的维护流程该更早和业务方明确责任人，否则别名补充会滞后。

E. 开放延伸类

E1. 知识库扩大 100 倍怎么办？ > ①向量库层面：Milvus 分区（按景区/业务线 partition）、HNSW 索引参数调优（efSearch 权衡召回率与延迟）；②检索层面：分层检索——先用轻量分类器把问题路由到业务线，再在子库内检索，避免全库海选；③粗召回通道加关键词/混合检索兜底。

E2. 怎么评估一个 RAG 系统的好坏？ > 分层：检索层（Top-K 命中率、MRR）→ 生成层（忠实度：答案是否忠于检索材料；相关性）→ 端到端（最终答案正确率）→ 线上（用户反馈率、人工接管率）。只看端到端无法归因，只看检索层会漏掉生成退化——四层都要有。

E3. 从零建一个问数系统你会怎么排？ > 先治理后智能：①先和业务定核心指标口径、建治理表（没有这个，模型再好也映射不对）；②小范围 MVP（十几个指标内）验证链路；③同步建回归集；④逐步扩指标面和问题复杂度。顺序错了（先上模型后治理）会一直在修口径问题。

1. 口语稿

30 秒版

我的科研课题是冬小麦产量估测模型 MSTGN-Wheat——融合遥感、气象、土壤三类数据，在田块尺度预测每块地的产量。模型两个核心设计：一是图注意力网络建模相邻地块的空间依赖，二是 Transformer 结合生育期做时序建模，端到端训练。精度相对线性回归、随机森林、LSTM 等基线提升 10%–18%；训练效率通过混合精度、多进程加载、图缓存优化提升约 30%。可解释性用扰动归因——遮住某段输入看预测变化，得到的重要性排序与农学规律一致。这个工作产出了两篇 SCI 论文。

2 分钟版

任务背景：产量预估关系粮食安全预警、农业保险定损和政策决策，传统人工抽样测产慢、贵、覆盖小，我们用卫星数据加深度学习做大面积、提前、按田块精度的估产。

数据是三源融合：遥感植被指数看长势、气象数据（积温、降水）看老天、土壤数据看地力，对齐到每个田块的时间序列。

模型叫 MSTGN-Wheat——多源数据的时空图网络。空间侧：把田块建成图，节点是地块、边是地理邻近关系，用图注意力网络让每块地按学出来的权重聚合邻居信息，因为小气候、土壤连续性、病虫害传播都是跨地块的。时间侧：用 Transformer 的自注意力读生育期内的生长序列，并注入生育期阶段编码——不同阶段对产量贡献不同，灌浆期最关键。整体端到端训练，直接从多源时序学产量。

实验：相对线性回归、随机森林、LSTM 基线，RMSE 相对下降 10%–18%；消融实验证明拆掉图模块精度明显掉。训练效率靠混合精度、多进程数据加载、图结构缓存提升约 30%。可解释性用扰动归因，重要性热力图和农学常识一致——这也是模型学到真实规律而非数据巧合的证据。

2. 先用大白话理解

任务 = 预测每块地能打多少小麦。 想象老农站在地头估产，他看三样东西：

  1. 看庄稼脸色——苗绿不绿（卫星照片代看，叫遥感；“脸色值”叫 NDVI）；
  2. 看老天爷——雨水够不够、积温足不足（气象数据）；
  3. 看地本身——地肥不肥（土壤数据）。

外加第四样暗知识：隔壁地的情况——连片地块的气候、土质、病虫害相通，隔壁长势好，你这块大概率也好。

4. 模型三件套（名字即卖点）

MSTGN-Wheat = Multi-source Spatio-Temporal Graph Network for Wheat：多源数据 · 时空 · 图网络。名字三个卖点对应三大件。

4.1 图注意力网络（GAT）——建模邻居影响

先用大白话理解

把全县田块看成关系网：每块地一个点，挨着的连一条线，消息在网上流动——每块地不但知道自己那点事，还知道邻居的。但邻居和邻居不一样：紧挨着、长势典型的影响大，隔条河的可能没关系。注意力就是让模型自己学”听哪个邻居的、听几分”。

展开讲

  • 建图：节点=田块（携带多源数据特征向量）；边=k 近邻（K-Nearest Neighbors，地理最近的 k 块）+ 距离阈值结合——太远不连，空间影响有范围；
  • GAT 核心：每条边算注意力系数——自己的特征和邻居特征拼接过小打分网络得 0~1 权重，新特征 = 自己 + 按权重加权的邻居特征；权重是学出来的；
  • 层数：一层=打听直接邻居，两层=邻居的邻居；用 2-3 层。层数过多会过平滑（Over-smoothing）——所有节点特征趋同一锅粥（主动提这个词加分）。

4.2 Transformer 时序模块——建模生长过程

先用大白话理解

产量是八九个月”攒”出来的，模型要读一本生长日记（每旬一页：脸色值+天气）。但每页重要性不同——灌浆期那几页最关键。Transformer 的本事是读日记时自动给每页标重要度，重点时期重点看。

展开讲

  • 自注意力：序列里每个时间点给其他时间点打相关分——5 月降水和 3 月 NDVI 谁更重要，模型自己学；天然契合”不同生育期贡献不同”的农学事实；
  • 位置编码 + 生育期编码：注意力本身不识先后，需附加”第几旬”标记；我们把生育期阶段标签（返青/拔节/灌浆）注入编码——这就是简历”结合生育期信息”的落地；
  • 为什么不用 LSTM（必考）：LSTM 逐格顺序读，长序列前忘后（长程依赖弱）且不能并行训练；Transformer 全局注意力 + 可并行，长序列和效率都赢。

4.3 多源融合 + 端到端

先用大白话理解

三条线索各有格式（卫星按景、天气按天、土壤一年一档），融合=对齐到同一块地同一段时间拼成完整档案；端到端=从档案到产量一口气学完，不靠人工定经验规则（“NDVI 低于 0.4 减产 10%”这种公式不需要人写，模型自己学）。

展开讲

  • 对齐是最脏最重的活：空间上遥感像元（Pixel，卫星照片的格子）按田块边界聚合；时间上统一重采样（Resampling）到旬；云遮挡的缺失期用前后插值（Interpolation）补；
  • 结构：三路各自过特征提取层，拼接（Concatenate）进时序模块——遥感时序主干，气象、土壤作条件注入；
  • 端到端对照传统两段式（人工算指数再回归），能学到人工特征表达不了的组合规律。

5. 训练流程与效率优化

先用大白话理解

学生刷历年真题：看历史年份的（档案 + 真实产量），让它猜；猜错把责任往回摊到几百万个参数上，各微调一点；重复几万次就会了。考试用没见过的年份考，防背题。提效 30% 三件套：算得快（16 位数代替 32 位）、备料快（多开工人并行准备数据让 GPU 不等饭）、不重复劳动（图的邻居关系提前算好存着，不每轮重建）。

展开讲

  1. 按年份划分数据——不能随机打散（同年地块相关，随机会”泄题”= 数据泄露）；
  2. 前向传播出预测 → 与真实产量算 MSE 损失 → 反向传播算每个参数的梯度 → 梯度下降小步调参（步长=学习率）；
  3. 全数据一遍 = Epoch，训几百轮，验证集损失不再降就早停（防过拟合）；
  4. 效率三件套：①AMP 自动混合精度（16 位浮点参与大部分计算，GPU 更快、显存省半，还能加大 Batch）；②DataLoader 多进程加载（num_workers，防”GPU 等饭”空转）；③图结构缓存（邻接结构、邻居索引不变，提前算好不再每轮重建）。

6. 可解释性：扰动归因（+归因三家族）

先用大白话理解

判断一道菜哪种调料最重要：每次少放一种，尝味道变了多少——变化最大的就是灵魂调料。模型同理：把某段输入遮住或打乱（比如抹掉灌浆期降水），看预测产量变多少——变幅大 = 模型依赖它 = 重要。

展开讲

  • 对每个时间步的每种数据源逐个置零/替换均值，记录预测变化幅度，得到重要性热力图；
  • 为什么必须做：①农学家和决策者不信任黑盒；②验证模型学到真规律（重要性排序和农学常识一致——灌浆期气象、返青期 NDVI 权重高——说明不是瞎拟合）；③发现异常（不该重要的输入权重高，往往提示数据泄露或假相关）；④给用户信任依据；
  • 扰动法的坑：特征相关时单点扰动误导（遮了降水，模型拿温度补位，低估降水贡献）——缓解：成组扰动（气象变量一起遮）。

IG 白话（防追问）：直接看梯度会”梯度饱和”——菜咸到头再加盐味道不变、敏感度≈0，单点梯度低估重要输入。IG 从基线（白开水版输入）沿路径一点点加料走到正常版，把全程瞬时敏感度累加——咸到头前那段路径已把贡献记足。公式口述：贡献 = (实际值−基线值) × 路径上梯度分量的积分（用几十小步求和近似）。

“为什么项目用扰动不用 IG”标准答： > “我们知道 IG，它理论性质好但要白盒求导、基线选择敏感。选扰动法三个原因：①语义贴合——解释单元是’某段时期某数据源’，’遮掉灌浆期降水看预测变多少’天然可读、农学直接可解释；②实现简单稳健，不依赖梯度质量；③数据源少（三类×十几时间步），扰动次数付得起，IG 的效率优势用不上。”

7. 问答库

A. 总体类

A1. 用两分钟介绍你的科研 → 第 1 章口语稿。顺序：背景意义 → 数据 → 模型两核心 → 实验结果 → 可解释性。

A2. 研究的创新点是什么？ > 三个：①田块尺度的时空联合建模——多数工作只在区域尺度或只做时序，我们用图结构把空间依赖显式建模；②生育期信息注入注意力编码——让”农时先验”参与建模而不只是排队列；③可解释性验证闭环——用扰动归因验证模型学到的规律与农学一致，而不只报精度数字。

A3. 科研和工程实习的关系？ > “科研教我从 0 提出并验证一个方法（假设-实验-消融的完整闭环），工程实习教我把方法变成可靠的服务（可测试、可灰度、可回滚）。我想做 AI 应用开发，正好两头都要。”

B. 技术深挖类

B1. 为什么要图结构？不用不行吗？ > 空间依赖是真实物理存在——小气候、土壤连续性、病虫害都跨地块传播。最有说服力的是消融实验：拆掉图模块（其余不变），精度明显下降，证明空间建模本身有效，不是堆料。

B2. 图怎么建的？边怎么定？ > 节点=田块；k 近邻 + 距离阈值结合。试过纯地理邻接（太稀疏）和纯 k 近邻（引入无关远邻），阈值 + k 近邻折中效果最好。

B3. 节点特征是什么？ > 每田块的多源时序特征向量：NDVI 时序 + 气象时序（积温、降水）+ 土壤静态特征（肥力等），按旬对齐堆叠。

B4. GAT 和 GCN 区别？ > GCN 邻居权重由图的度数固定；GAT 的注意力权重是训练学出来的自适应权重。我们的场景邻居影响不均等（方向、面积、长势都影响），GAT 合适。

B5. GAT 注意力怎么算？ > 每条边：两节点特征各自过变换矩阵，拼接后过 LeakyReLU 打分得到 e_ij，对节点所有邻居 softmax 归一化成权重 α_ij，新特征 = 自身 + Σ α_ij × 邻居特征，多头（Multi-Head，几套独立注意力各算各的最后拼接）增强稳定性。

B6. 多源数据粒度不一致怎么办？ > 时间统一重采样到旬；空间上遥感像元按田块边界聚合均值；土壤静态特征复制到各时间步或作条件注入；缺失期插值补齐。

B7. 为什么 Transformer 不用 LSTM？ > LSTM 顺序处理：长序列读到后面忘了前面（长程依赖弱），且逐步计算无法并行、训练慢。Transformer 自注意力全局直达 + 可并行。生育期序列是典型的”长序列 + 关键期稀疏”结构，正适合。

B8. 怎么防过拟合？ > 按年份划分（防泄露）、早停、Dropout、控制模型容量；数据增强手段有限（农时不可造），主要靠前几项。

B9. 泛化性？换省份还行吗？ > 跨区域会掉点——气候、品种、农作制度不同。诚实答”论文里也讨论了这个局限，跨区需要局部微调”，比吹”全国通用”可信。

B10. 训练效率 30% 怎么来的？ > 三件套：AMP 混合精度（16 位计算省时省显存）、DataLoader 多进程加载（GPU 不等饭）、图结构缓存（不每轮重建）。单看各项 10% 上下，合计约 30%。

B11. 精度 10-18% 为什么是区间？ > 相对不同基线（线性回归/随机森林/LSTM/消融版）、不同区域年份的测试集，RMSE 相对下降幅度不同——弱基线（线性回归）提升接近 18%，强基线（LSTM）约 10%。

B12. 扰动归因和 IG 是一回事吗？（高频陷阱题） > 不是。扰动是黑盒试错派（改输入看输出），IG 是白盒求导派（基线到输入积分梯度，解决单点梯度饱和问题），SHAP 是博弈论分账派。我们选扰动：语义贴合”遮某段时期”、实现稳健、特征数少成本可付。详见第 6 章对比表。

C. 难点类

C1. 研究里最难的是什么？ > “两件：①多源数据对齐——占了大半时间，遥感受云遮挡、气象站点稀疏、土壤一年一档，把三者对齐到’每田块每旬’是纯脏活，但决定了上限；②图的边定义——太稀疏欠表达、太密引入噪声邻居，最后靠消融实验选的阈值+k 近邻。共同的教训：科研里’怎么定义问题和对齐数据’比’选什么模型’更决定成败。”

C2. 中间走过什么弯路？ > 一开始只用时序模型（LSTM），精度卡住；可视化误差地图发现误差呈空间聚集——相邻地块一起错，说明缺空间信息，才引入图结构。这个”从误差分布反推缺失建模维度”的过程比结果更值得讲。

C3. 如果继续做，下一步是什么？ > 跨区域泛化（元学习/迁移微调）、极端年份鲁棒性（干旱年样本少）、多作物扩展；工程上想做估测服务化——把模型包成 API 给保险定损用，正好接我的工程实习方向。
